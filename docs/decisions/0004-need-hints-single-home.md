# 0004 需求的做法只写在一处

- 状态：已采纳
- 相关代码：`pet/brain/context_builder.py`（`_NEED_HINTS`、`_build_feeling`、`_need_hint`）

## 背景

早期版本把「该怎么做」写在感受描述里（「饿得肚子咕咕叫！马上向用户讨吃的，或者立刻自己生成食物吃掉！」），
同时需求章节又给了一遍建议做法。同一件事有两处祈使句时，模型的注意力会被分散，
而且 `FOOD_ENABLED=False` 时感受描述还会给出做不到的建议（自己生成食物）。

## 决定

- **做法只写在 `_NEED_HINTS`**（连同按时段覆盖的作息文案），由「你惦记着的事」章节输出；
- `_build_feeling` 只描述感受，不出现祈使句；
- 其余静态块（`_SELF_LIFE_GUIDE`）、任务段（`_chat_task` 等）与自主 user prompt 只做抽象引导
  （「言行要反映当前状态」「见『你惦记着的事』」），同样不重复具体做法；
- 特例：理智极低时的安全底线（「绝不写或覆盖文件、打开未知网页、调用改动用户环境的工具」）保留在感受描述里——
  它是**输出约束**而非需求引导，不属于「怎么做」；
- 觅食关闭时 `_need_hint` 把「自己生成食物」替换为「向用户讨点吃的」。

## 后果

- 一个需求只有一个做法来源，改文案不会两处打架；静态块与 user prompt 里也不留重复做法，
  否则「两处指令、模型任选其一」的老问题会从别处回来；
- 代价：读 `_build_feeling` 的人要意识到它「只描述感受」这一点（有测试断言 feeling 里不含行动引导）。
